# План личного кабинета (аккаунт, авторизация, синхронизация)

Черновик плана на будущее -без реализации, без установки зависимостей, без миграций. Отдельный файл от [prisma-schema.md](prisma-schema.md) осознанно: там -схема для раздела «Статьи» (контент-логика), здесь -личный кабинет пользователя (аккаунт-логика). Разные домены задачи, разные решения, незачем смешивать в одном файле.

**Условие возврата к этому плану:** явное решение пользователя начать реализацию -не раньше. Пункт уже отмечен в `plan.md` (Этап 23, «Требует бэкенда/внешнего сервиса»: «аккаунт с историей между устройствами») как отложенный без даты. Здесь -детализация на случай, когда решение созреет.

---

## Зачем это вообще нужно

Сейчас профиль (зарплата/стаж/дети) и история расчётов уже работают -полностью на клиенте, через `localStorage` ([lib/profile.ts](lib/profile.ts), история в [Calculator.tsx](components/Calculator.tsx)). Это осознанный выбор всего проекта (см. `plan.md`, Этап 20-21): без бэкенда, без авторизации, работает сразу.

Личный кабинет решает ровно одну проблему, которую `localStorage` в принципе не может решить: **данные привязаны к конкретному браузеру на конкретном устройстве.** Если пользователь открывает сайт с телефона и с рабочего компьютера -профиль и история не совпадают. Всё остальное (сами расчёты, интерфейс) уже отлично работает без аккаунта.

## Главный принцип: аккаунт -это надстройка, не замена

Гостевой сценарий (без входа, всё в `localStorage`) должен продолжать работать полностью, всегда -это то, что уже отличает сайт от конкурентов («без регистрации», см. `siteConfig`/футер на каждой странице). Личный кабинет -прогрессивное улучшение поверх, а не обязательное условие для пользования сайтом.

Практическое следствие: при входе в аккаунт нужен явный шаг **переноса гостевых данных** -предложить залить то, что уже накопилось в `localStorage` этого браузера, в аккаунт (один раз, при первом входе), а не молча игнорировать или молча перезаписывать.

## Аутентификация

Не решено, что из этого списка. Кандидаты (App Router, Next.js 16):

- **Auth.js (бывший NextAuth)** -стандартный выбор для Next.js, есть готовый Prisma-адаптер (`@auth/prisma-adapter`), умеет и OAuth-провайдеров, и email+пароль
- **Провайдеры входа:** Яндекс ID -вероятно приоритетный для русскоязычной аудитории сайта (есть готовый OAuth-провайдер), плюс, возможно, обычная почта+пароль как запасной вариант без сторонних сервисов. Google/VK -по необходимости, не обязательны с самого начала
- **Стратегия сессии:** database-сессии через Prisma (проще инвалидировать, чуть больше нагрузка на БД на каждый запрос) vs JWT (быстрее, сложнее принудительно разлогинить). Для сайта такого масштаба разница не критична -решить по вкусу при реализации, не блокирующий вопрос

## Модель данных (черновик, будет уточняться)

```prisma
model User {
  id            String    @id @default(cuid())
  email         String?   @unique
  createdAt     DateTime  @default(now())

  profile       Profile?
  history       CalculationHistoryEntry[]
}

// 1:1 с User -прямое соответствие текущей структуре lib/profile.ts (ProfileValues)
model Profile {
  id              String   @id @default(cuid())
  userId          String   @unique
  user            User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  monthlyIncome   Float?
  insuranceYears  Float?
  childrenCount   Float?
  updatedAt       DateTime @updatedAt
}

// Аналог записи истории в Calculator.tsx (HistoryEntry), но привязанной к аккаунту, а не к
// localStorage конкретного браузера
model CalculationHistoryEntry {
  id            String   @id @default(cuid())
  userId        String
  user          User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  calculatorSlug String  // по slug из lib/calculators/registry.ts -как и в prisma-schema.md,
                         // не отдельная модель/FK, единственный источник правды -код
  values        Json     // те же CalculatorValues, что уже пишутся в localStorage
  summary       String   // готовая строка-превью, как summarizeResult() в Calculator.tsx
  createdAt     DateTime @default(now())
}
```

Сознательно не проектирую здесь глубже (индексы, лимиты на количество записей и т.п.) -рано, пока нет решения даже начинать.

## Клиентское состояние: нужен ли Zustand

Отдельно поднятый вопрос -отвечаю здесь явно, чтобы не потерялось.

**Сейчас -нет.** Ни расшаренного, ни часто обновляемого клиентского состояния между несвязанными компонентами в проекте не появится сразу вместе с аккаунтом. То, что появится в первую очередь -это данные, читаемые в серверных компонентах (профиль, история пользователя со страницы кабинета) без какого-либо клиентского state-менеджера вообще, и точечные Server Actions на запись (обновить профиль, сохранить расчёт).

**Где клиентское состояние всё же понадобится:** статус сессии в шапке сайта (залогинен/нет, чтобы показать имя вместо кнопки входа) -это тоже не повод для Zustand, обычного React Context поверх `useSession()` из Auth.js достаточно, он уже это умеет из коробки.

**Когда пересмотреть:** если появится полноценный интерактивный экран личного кабинета с частым обновлением состояния сразу в нескольких несвязанных местах интерфейса одновременно (не просто список истории, а что-то вроде живого дашборда) -тогда Zustand (или Jotai) обоснован, и это будет видно по реальной боли при разработке, а не заранее.

## Миграция гостевых данных при регистрации

Не спроектировано подробно, но принцип: при первом входе в аккаунт -прочитать текущий `localStorage` этого браузера (профиль + история), предложить пользователю перенести в аккаунт (не молча), затем можно почистить `localStorage` или оставить как есть -некритично, данные не потеряются в любом случае.

## Что сознательно не входит в этот план

- **Платежи/подписки** -если появится платная фича (например, пакетный калькулятор для бухгалтеров, уже отмечен в `plan.md` как «единственный реальный кандидат в платную фичу»), это отдельное архитектурное решение поверх аккаунта, не часть этого плана
- **Админ-панель** -не про пользователей сайта, а про редактирование контента; это уже покрыто (в теории) `prisma-schema.md`, разные системы
- **Комментарии, лайки, публичные профили** -не обсуждались, не проектируются заранее без явной необходимости (тот же принцип, что и в `prisma-schema.md`)
- **Zustand/Jotai и другие клиентские state-менеджеры** -см. раздел выше, осознанно не добавляется заранее
