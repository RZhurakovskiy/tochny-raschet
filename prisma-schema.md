# Схема Prisma для раздела «Статьи» (SEO-контент)

Черновик схемы данных для будущей админки на Prisma + PostgreSQL. Это только план данных -без установки Prisma, без миграций, без бэкенда. Пользователь дополняет этот файл постепенно, по мере того как проясняются детали.

**Область применения:** только новый раздел «Статьи»/база знаний (Этап «Раздел статей» из `plan.md`) -отдельные информационные материалы, не привязанные к вводу конкретных цифр (например, «что такое НДФЛ простыми словами»).

**В схему НЕ входит весь остальной SEO-текст сайта, а не только формулы** -это два разных решения, стоит развести явно:

1. **Формулы/расчётная логика** (`lib/calculators/*.ts`) -не входят никогда, ни при каких условиях. См. «Главный принцип» ниже.
2. **Пояснительный текст и FAQ внутри самих страниц калькуляторов** (`explanation`/`faq` в `app/ndfl/page.tsx`, `app/peni/page.tsx` и т.п.) -тоже сознательно не входят в эту схему, но по другой причине: этот текст не самостоятелен, он привязан к конкретной формуле -примеры расчёта в нём («доход 5 000 000 ₽ → налог 702 000 ₽») обязаны совпадать с тем, что реально считает калькулятор. В этом плане несколько раз находились расхождения между написанным «с головы» примером и живым расчётом (см. `plan.md`, Этап 16) -именно потому, что текст и формула правились и проверялись в одном заходе, в браузере. Если этот текст переедет в CMS, редактируемую отдельно от кода, эта связка ломается: правку через админку никто не сверит с живым калькулятором, и устаревший пример тихо повиснет на проде.

Второй пункт -менее однозначное решение, чем первый (в отличие от формул, здесь можно спорить в пользу единообразия редактирования). Если решите пересмотреть -тогда понадобится либо держать примеры расчёта отдельно от остального текста и генерировать их кодом (не текстом из CMS), либо явный процесс сверки при каждой правке через админку.

## Главный принцип: данные vs логика

Прежде чем сама схема -ключевое архитектурное решение, от которого всё остальное отталкивается.

**Через админку -только контент (проза):** заголовки, текст статей, meta-описания, FAQ-вопросы/ответы, ключевые слова. Это данные, ошибка в них -опечатка, а не сломанный расчёт.

**Через код -вся расчётная логика и формулы, всегда:** `lib/calculators/*.ts` остаётся как есть, недоступным для админки в принципе, не только «пока не сделали». Причины:

1. **Формула -это не текст, это функция с типами.** Прогрессивная шкала НДФЛ, доли алиментов, проценты по стажу -в TypeScript они проверяются компилятором (`tsc --noEmit`), их можно прогнать скриптом на граничных значениях (так и делалось весь этот план -см. `plan.md`, там почти на каждом этапе формулы «проверены скриптом»). Формула, введённая через текстовое поле в админке (даже как «настраиваемое выражение»), теряет всё это -опечатка в выражении обнаружится только когда пользователь сайта получит неверную сумму по налогу.
2. **Уже отработанная в этом проекте дисциплина проверки** (веб-поиск перед публикацией цифры, `npm run build` после каждой правки, ручная проверка в браузере) годится только для code review -в потоке «отредактировал текст в CMS → нажал "опубликовать"» этой дисциплины физически неоткуда взяться.
3. Сайт сознательно полностью статический (SSG, см. `plan.md`, Этап 11/21) -каждый расчёт выполняется чистой JS-функцией в браузере пользователя. Если бы часть формулы жила в БД, калькулятору пришлось бы либо тянуть конфиг во время сборки (усложняет пайплайн ради сомнительной пользы), либо становиться динамическим (теряет часть SEO-преимуществ статики).

**Про регуляторные константы (МРОТ, ключевая ставка ЦБ, предельная база СФР, ставки НДФЛ) -отдельный случай, но ответ тот же, пока что.** Технически это просто числа, не логика -в этом смысле они ближе к «данным», чем формулы. Но:

- Меняются редко (МРОТ и база -раз в год, ставка ЦБ -после каждого заседания, несколько раз в год) -неудобство от правки кода вместо админки минимальное.
- Уже вынесены в один файл [lib/calculators/constants.ts](lib/calculators/constants.ts) с комментариями-предупреждениями («⚠️ проверить актуальное значение при использовании после 2026 года») -одно место, а не разбросано по коду.
- Каждое обновление в этом плане проходило через веб-поиск с датированными источниками (см. `plan.md`, Этап 16.2 -перепроверка 27 фактов). Админ-форма с полем «Ключевая ставка ЦБ, %» такой проверки не потребует -будет соблазн просто вписать число.

**Вывод: не переносить константы в БД сейчас.** Если через год-два ручное обновление 1-2 раза в квартал станет реально обременительным -можно добавить отдельную таблицу `RegulatoryConstant` с полями `key/value/sourceUrl/verifiedAt` специально под это, отдельно от статей. Но это осознанное решение на будущее, не часть текущей схемы.

## Модели (Prisma schema, черновик)

```prisma
enum ArticleStatus {
  DRAFT
  PUBLISHED
  ARCHIVED
}

model Article {
  id                String    @id @default(cuid())
  slug              String    @unique

  // SEO и заголовки -по аналогии с тем, как устроены калькуляторы в lib/calculators/registry.ts
  title             String
  metaDescription   String
  excerpt           String?   // короткое превью для карточек в списке статей

  // Тело статьи -формат ещё не решён, см. "Открытые вопросы" ниже
  content           String

  status            ArticleStatus @default(DRAFT)
  publishedAt       DateTime?
  createdAt         DateTime  @default(now())
  updatedAt         DateTime  @updatedAt

  // Категория -по СУЩЕСТВУЮЩЕМУ slug'у из CATEGORIES в lib/calculators/registry.ts,
  // не отдельная таблица и не FK -см. "Почему категория не отдельная модель" ниже
  categorySlug      String?

  // Внутренняя перелинковка на калькуляторы -тоже по slug'ам, не FK
  relatedCalculatorSlugs String[]

  // Ключевые слова -по аналогии с mainKeyword/secondaryKeywords у Calculator
  mainKeyword       String?
  secondaryKeywords String[]

  // E-E-A-T -по аналогии с SourceNote.tsx у калькуляторов
  sourceLabel       String?   // например "ст. 224 НК РФ"
  sourceUrl         String?
  dataUpdatedAt     DateTime? // "данные актуальны на" -если статья ссылается на регуляторные цифры
  author            String    @default("Роман Жураковский")

  faqItems          FaqItem[]
}

model FaqItem {
  id        String   @id @default(cuid())
  articleId String
  article   Article  @relation(fields: [articleId], references: [id], onDelete: Cascade)
  question  String
  answer    String
  order     Int      @default(0)
}
```

### Почему категория -не отдельная модель

`CATEGORIES` уже живёт в коде ([lib/calculators/registry.ts](lib/calculators/registry.ts)) и используется калькуляторами. Если завести отдельную таблицу `Category` в БД -получится два независимых источника правды об одних и тех же 5 разделах сайта, которые придётся синхронизировать вручную при любом изменении. Проще и безопаснее: `Article.categorySlug` -обычная строка, которая должна совпадать с одним из slug'ов в `CATEGORIES`, а сверку (что такая категория существует) делать на уровне приложения при сохранении статьи, а не на уровне БД.

То же самое решение -и для `relatedCalculatorSlugs`: список калькуляторов остаётся полностью в коде, статья просто хранит их slugs как строки для перелинковки.

## Открытые вопросы (дополнять по мере решения)

- [ ] **Формат `content`.** Варианты:
  - **Markdown/MDX** -быстрее писать, но нужен рендерер, который приведёт markdown к тому же визуальному стилю, что и `ContentSection`/таблицы/примеры на страницах калькуляторов (иначе статьи будут выглядеть иначе, чем остальной сайт)
  - **Структурированный JSON** (массив секций `{title, body, highlight}`, по образцу того, как `explanation` устроен у калькуляторов через `<ContentSection>`) -визуально стопроцентно совпадёт с калькуляторами, но писать статьи через админку станет чуть менее гибко (нельзя просто "написать текст", нужно раскладывать по секциям)
- [ ] Нужен ли предпросмотр статьи перед публикацией (сравнить, как она встанет в общий шаблон сайта) -если формат `content` markdown, предпросмотр практически обязателен
- [ ] Нужна ли история версий статьи (кто и когда правил) -или достаточно `updatedAt`
- [ ] Один автор («Роман Жураковский» строкой) или отдельная модель `Author`, если авторов станет больше
- [ ] Нужны ли теги отдельно от категории (categorySlug -один на статью, теги -многие ко многим) -если объём статей вырастет и одной категории на всё будет мало
- [ ] Черновик vs публикация -вероятно на уровне Next.js это ISR/on-demand revalidation при смене статуса на `PUBLISHED`, а не полный `npm run build` при каждой статье; сама схема хостинга/ревалидации ещё не спроектирована

## Что подтвердилось на практике (после трёх реальных статей, 27.08.2026)

Пока раздел «Статьи» существует только в коде ([lib/articles/registry.ts](lib/articles/registry.ts), без БД), но три написанные статьи уже кое-что прояснили из списка открытых вопросов выше -фиксирую, чтобы не потерять при переносе в реальную схему.

- **`categorySlug` в реальном коде не понадобился и не используется вообще.** Все три написанные статьи -«сценарные» разборы, которые намеренно пересекают несколько категорий калькуляторов сразу (например, статья про сокращение ссылается на калькуляторы из «Отпуска и увольнение» И «Зарплата и налоги» одновременно). Привязка к одной категории для такого формата статей плохо подходит. В реальном `Article` в коде этого поля сейчас нет. Вывод: либо делать поле по-настоящему необязательным и не полагаться на него в навигации, либо для статей вообще не использовать категории калькуляторов, а придумать свою независимую таксономию, если/когда она понадобится
- **FAQ на практике живёт не в registry, а в отдельной карте прямо в файле роута** (`app/blog/[slug]/page.tsx`, `ARTICLE_FAQ: Record<string, FaqItem[]>`), а тело статьи -в третьем месте (`components/articles/*.tsx`). То есть у одной статьи сейчас три места правки вместо одного. Для чистого кода это нормально (примерно как у калькуляторов -форма и текст страницы тоже разнесены по разным файлам), но при переносе в БД это явный сигнал: `FaqItem` как отдельная модель с `articleId` (уже так спроектировано в схеме ниже) -это не только чище, а ещё и объединяет три места в одно, что для админки прямо важно
- **Формат содержимого-секциями (`ContentSection`) подтвердил себя на практике, включая необходимость таблиц внутри секции** (у статьи про самозанятость есть сравнительная таблица условий страхования прямо в тексте, не только в примерах у калькуляторов). Это аргумент в пользу структурированного JSON с поддержкой хотя бы: параграф, список, таблица, выделенная секция (`highlight`) -а не просто «текст» одной строкой
- **Стиль пунктуации -реальная договорённость, а не мелочь.** С 27.08.2026 весь новый текст статей использует настоящее тире «—» (с пробелами по обе стороны) вместо обычного дефиса `-`, которым по инерции был написан весь более ранний текст сайта. Когда дойдёт до реальной админки -стоит явно прописать это в редакторских рекомендациях (или даже проверять авто-линтером текста), а не полагаться на память

## Что сознательно не входит в схему

- **Калькуляторы и их формулы** -остаются в `lib/calculators/*.ts` и `lib/calculators/registry.ts`, полностью в коде, без исключений. Это ответ на вопрос «а формулы тоже через админку?» -нет, никогда, см. «Главный принцип» выше
- **Пояснительный текст и FAQ на страницах самих калькуляторов** (`app/*/page.tsx`) -тоже остаются в коде, но по отдельной причине (привязка примеров к живому расчёту, не про безопасность формул) -см. «Область применения» выше. В CMS идут только самостоятельные статьи, не привязанные к конкретному калькулятору
- **Регуляторные константы** (МРОТ, ставка ЦБ и т.п.) -остаются в `lib/calculators/constants.ts`, пока ручное обновление не станет реальной проблемой (см. рассуждение выше)
- **Категории калькуляторов** -остаются в коде, статьи только ссылаются на них по slug
- Пользовательские аккаунты, комментарии, лайки -не обсуждались, не проектируются заранее без явной необходимости
